# Стандарт анализа в SDLC

Это локальный эталонный пакет, а не внешний репозиторий. Без отдельного разрешения его нельзя подключать к корпоративным API или моделям.

Пакет задаёт:

- накопительный базовый процесс из трёх уровней зрелости, `1 → 2 → 3`;
- необязательные блоки «С моделью» на каждом уровне: модель готовит черновик и замечания, одобрение дают люди;
- контракт продуктового метарепозитория;
- раздельное владение продуктом и сервисами;
- безопасные, явные и доступные только для чтения снимки сервисов;
- последовательную проверку разными ролями;
- версионированные обновления через запросы на слияние (Merge Request, MR) без скрытой перезаписи;
- границу между спецификацией аналитика и `design.md`, исключения из правил и порядок срочных изменений.

Текущая версия пакета записана в `VERSION` и `manifest.json`. В `manifest.json` также перечислены продуктовые файлы, которые обновление не может перезаписывать. Переносимая реализация находится в `tools/`; `Makefile` только вызывает её npm-команды.

## Источники истины

| Система | Чем владеет |
| --- | --- |
| Jira | Цель, приоритет, исполнитель, состояние процесса |
| Продуктовый метарепозиторий | Граница продукта, доменный язык, сквозные требования, продуктовый OpenSpec, прослеживаемость |
| Репозиторий сервиса | Код, локальные контракты и ADR сервиса, сервисный OpenSpec |
| Confluence | Доступное только для чтения зеркало принятого состояния Git |

Основная раскладка — в метарепозитории лежит папка требований OpenSpec — Store (хранилище требований); на неё указывает строка `store:` в config.yaml кода, это не третий репозиторий. Рядом `services.lock.yaml` с закреплёнными версиями сервисов; один репозиторий для кода и требований — вариант для маленького продукта с одним сервисом; отступления от раскладки оформляются по разделу [«Исключения из правил»](#исключения-из-правил).

## Основные команды

В эталонном `Makefile` намеренно нет команд публикации или записи в сервисный репозиторий.

Сначала установите зависимости из корня метарепозитория по его lock-файлу:
`npm ci`. Затем перейдите в `standards/sdlc-analysis-standard` и запустите
доступные локальные проверки:

```text
make bootstrap
make doctor
make validate
make test
```

Чтобы проверить обновление без изменения продуктового репозитория:

```text
npm run update:dry-run -- --product /path/to/product-meta
npm run update:patch -- --product /path/to/product-meta --output /path/to/sdlc-standard.patch
```

Патч содержит только явное изменение закреплённой версии и сохраняет оформление
остальной части lock-файла. Человек проверяет и применяет его через запрос на слияние (MR).
Файлы `CONTEXT.md`, `product.yaml`, `openspec/` и `services.lock.yaml` остаются
во владении продукта.

`bootstrap` запускает `doctor`: проверяет наличие файлов стандарта и не
устанавливает зависимости, не подключается к сервисам и не создаёт снимки.

Параметр `SERVICE` и команды `refresh`/`clean-snapshots` относятся к будущему
контуру и пока не являются интерфейсами этого пакета. Будущая работа со
снимками должна сверять идентификатор, классификацию и полный SHA по продуктовому
lock-файлу и использовать только временные снимки для чтения вне дерева исходного
кода.

## Контроль ревью

Ревью — одобрение владельца продукта (владельца решения) — оно же
принятие — и комментарии аналитика и техлида. Архитектор
подключается по признакам (данные, интеграции, безопасность,
производительность) или при споре. Слияние выполняет техлид (роль Maintainer).

Архитектор не читает каждую спецификацию. Если изменение затрагивает данные,
интеграции, безопасность, производительность или вызывает спор, аналитик
приглашает архитектора через `@` в MR и называет признак.

Перед уровнем 2 проверьте возможности платформы и тарифа:

1. защищена ветка по умолчанию, слияние — только Maintainer;
2. прямой push запрещён;
3. подтверждения владельца продукта, аналитика (не автора запроса) и техлида
   независимы, автор не одобряет свой запрос;
4. после новых коммитов подтверждения сбрасываются;
5. конвейер проверок обязателен.

Если платформа не может технически обеспечить правило, процесс помечается как `ручной`, а не как `автоматически защищённый`. Допустимые отклонения от правил описаны в разделах «Исключения из правил» и «Срочные изменения» ниже.

GitLab Community Edition 15.10 проверяет сам только пункты 1, 2 и 5 («Pipelines
must succeed»). Пункты 3 и 4 — требования стандарта, которые в этой редакции
держатся на договорённости и шаблоне запроса
[`templates/gitlab/merge_request_templates/Default.md`](templates/gitlab/merge_request_templates/Default.md)
(кладётся в `.gitlab/merge_request_templates/Default.md` репозитория). В платной
редакции они проверяются автоматически.

## Граница спецификации аналитика и design.md

Спецификация аналитика отвечает на «что и почему», `design.md` — на «как устроено». Это разделение, а не «меньше деталей, чем в прежних функциональных требованиях». Исключения оформляются по разделу [«Исключения из правил»](#исключения-из-правил).

В шапке `specification.md`, до первого раздела `##`, обязательно одно поле
`Архитектурный разбор` с одним из значений:

- `не требуется` — признаков для подключения архитектора нет;
- `запрошен (<признак>)` — вместо `<признак>` укажите `данные`, `интеграции`,
  `безопасность`, `производительность` или `спор`;
- `design.md: <ссылка>` — вместо `<ссылка>` укажите ссылку на принятое решение,
  например `[Решение](design.md)`.

Команда `make validate` проверяет наличие и допустимое значение этого поля
в шаблоне `templates/specification.md`. При подготовке изменения аналитик
обновляет значение в своей спецификации.

Архитектор создаёт свою ветку от ветки изменения и сохраняет `design.md`
в папке того же изменения. Затем открывает MR из своей ветки в ветку изменения,
как при переносе изменения из ветки шага 2 курса в ветку шага 1 курса. Аналитик одобряет соответствие решения требованиям;
после принятия решения указывает ссылку на `design.md` в шапке спецификации.

Аналитик пишет так, чтобы разработчик не додумывал бизнес-правила, а проверяющий отличал верный результат от неверного:

- поля и ограничения, состояния, права, ошибки, источники данных;
- измеримые нефункциональные требования;
- для фоновой обработки — момент запуска, допустимая задержка, последствия повтора и сбоя;
- схема внешнего сообщения, если она служит контрактом требований.

В `design.md` — выбор планировщика, очереди, обработчика, таблиц и индексов. Заданное техническое ограничение попадает в требования как ограничение со ссылкой на источник. Автор `design.md` и проверяющий — разные люди; в маленькой команде документ может написать аналитик, но отдельным файлом и с отдельным одобрением. Объём деталей определяют риск и проверяемость.

| Требование (спецификация) | Проектное решение (`design.md`) |
| --- | --- |
| Отчёт о просрочках формируется каждую ночь и доступен до 07:00; повторный запуск не создаёт дубликатов строк. | Ночное задание в 02:00, очередь заданий, уникальный ключ по дате и счёту, индекс по дате. |

## Исключения из правил

Исключения нужны и допустимы, если они описаны. Раздел действует для всех правил стандарта; отдельные правила (раскладка репозиториев, граница детализации, одобрение) ссылаются на него.

- **Когда допустимо:** выполнение правила в срок невозможно или вредно (срочная бизнес-доработка, авария на проде, ограничение платформы), и риск понятен.
- **Кто разрешает:** владелец решения; архитектор подключается по тем же признакам, что и в основном правиле (данные, интеграции, безопасность, производительность), или при споре. Автор исключение себе не разрешает.
- **Что фиксируется:** причина, какое правило и на какой срок смягчено, кто разрешил, цена задержки и риск, какое одобрение остаётся обязательным.
- **Как возвращаемся:** срок и владелец возврата к обычному пути указаны сразу; после исключения недостающие документы и ревью оформляются запросом на слияние (MR) со ссылкой на фактический выпуск, а не задним числом «как будто согласовано».

Сокращённый состав проверяющих допустим только по правилу, утверждённому заранее, с перечисленными условиями; независимая техническая проверка сохраняется и в сокращённом составе. Обход проверок платформы исключением не является.

## Срочные изменения

Частный случай раздела «Исключения из правил». Различаются два случая.

**Срочная бизнес-доработка.**

1. Владелец решения фиксирует причину срочности и цену задержки.
2. Сокращаются объём и очередь: замысел по одной фразе на часть, сценариев столько, сколько нужно для изменённого поведения и рисков; ревью идёт вне очереди.
3. Обязательное одобрение остаётся до выпуска. Сокращённый состав — только по заранее утверждённому правилу. Архитектор подключается по признакам основного правила (данные, интеграции, безопасность, производительность) или при споре.
4. Автор себя не одобряет; изменение идёт запросом на слияние, не мимо Git.

**Авария на проде.**

1. Действует процесс управления инцидентами; решение принимает уполномоченный ответственный.
2. Сначала минимальное обратимое действие: откат или отключение функции, затем минимальное исправление.
3. Фиксируются инцидент, исполнитель, версия, основание и проверка, а также способ отката либо причина, почему отката нет.
4. После восстановления оформляются недостающая спецификация и ревью со ссылкой на фактический выпуск, без имитации согласования задним числом. Код сверяется со спецификацией не позднее следующего рабочего дня (срок — предложение; утверждает владелец стандарта).

Для учёта срочных изменений ведутся метка срочности и её доля среди изменений, причины, повторные аварии и просроченный долг по спецификации.

## Intent этапа 1

Шаблон `templates/intent.md` описывает намерение этапа «Намерение и план».
Он расширяет шаблон курса анализа: шапка, проблема, результат, признаки успеха
с полями измерения, границы, открытые вопросы, план изменений, риски.
Владелец продукта пишет документ и одобряет его; аналитик помогает вопросами
и границами. Примеры курса анализа остаются валидными без правок.

Структуру проверяет `tools/intent-lint.ts`:

```text
npm run intent:lint -- <файл> [--mode analysis|stage1]
```

- `analysis` — шапка (инициатор, владелец решения, состояние, источник)
  и разделы старого образца: проблема, результат, границы, признаки успеха,
  открытые вопросы. Каждый раздел непустой, без заглушек `<…>`.
- `stage1` — то же плюс поля измерения в «Признаках успеха» (метрика, «до»,
  цель, срок проверки, способ измерения, ответственный), таблица
  «Плана изменений» и раздел «Риски».

Проверка структурная, а не смысловая: структура ≠ смысл; рецензент проверяет,
что описана проблема, а не решение. Структурно полный документ с формальным
эффектом проходит линтер и возвращается рецензентом.
