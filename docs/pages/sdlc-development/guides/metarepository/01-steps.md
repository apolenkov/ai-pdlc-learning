## Шаг 1. Найдите свой продукт {#find-product}

Откройте `README.md` метарепозитория. В корне прочитайте `CONTEXT.md` — границы продукта и словарь — и `AGENTS.md`, затем в карточке `product.yaml` посмотрите владельцев и ссылки. Убедитесь, что идентификатор задачи ведёт к нужному продукту, а ссылки на Store <code class="meta-token">product-specs</code> и на оба репозитория кода, <code class="meta-token">web</code> и <code class="meta-token">api</code>, доступны. Если ссылка или владелец неизвестны, уточните их у организатора до работы с кодом.

## Шаг 2. Возьмите проверенную версию кода {#workspace}

Проверенная версия нужна для каждого затронутого репозитория кода: общий Store и идентификатор изменения не заменяют его SHA. Для анализа используйте выбранный снимок кода, доступный агенту только для чтения. Отделённый `HEAD` сам по себе не запрещает менять файлы: режим чтения обеспечивается средой исполнения. Запишите SHA каждого репозитория.

Для реализации создайте отдельный worktree внутри репозитория кода: он использует Git-данные этого репозитория, а исходники не переезжают в <code class="meta-token">meta-repo</code>. Семантика `worktree add -b` описана в [документации Git](https://git-scm.com/docs/git-worktree).

Перейдите в корень репозитория кода: дальше команды выполняются оттуда.

```sh
cd /absolute/path/to/web
```

Увидите: приглашение терминала уже в каталоге `web`; сама команда ничего не печатает.

Проверьте, что коммит из карточки задачи доступен локально. Вместо значения SHA подставьте полный SHA своего репозитория. Суффикс `^{commit}` проверяет, что значение — именно коммит, а не тег или ветка.

```sh
git rev-parse --verify "<SHA>^{commit}"
```

Увидите: тот же полный SHA. Ошибка `fatal: Needed a single revision` — коммита нет локально: сверьте карточку с организатором.

Проверьте состояние рабочей копии.

```sh
git status --short
```

Увидите: пустой вывод, если незакоммиченных изменений нет.

Посмотрите список рабочих копий репозитория.

```sh
git worktree list
```

Увидите: строку `<путь> <короткий SHA> [main]` для каждой рабочей копии.

Создайте рабочую копию на проверенном коммите.

```sh
git worktree add -b feat/exp-001-export .worktrees/exp-001-export <SHA>
```

Увидите: `Preparing worktree (new branch 'feat/exp-001-export')` и `HEAD is now at <короткий SHA> <сообщение>`.

Сверьте, что в новой рабочей копии тот же коммит. Ключ `-C` выполняет команду в указанной папке без перехода в неё.

```sh
git -C .worktrees/exp-001-export rev-parse HEAD
```

Увидите: тот же полный SHA, что записан в карточке задачи.

Повторите для второго затронутого репозитория — со своей веткой, путём и SHA. Зависимости, команды запуска и проверки берутся из инструкций самого репозитория; убедитесь, что его Git-хуки работают в новом worktree. Каталог `.worktrees/` должен быть исключён из отслеживания по правилам репозитория. После доставки результата чистый worktree удаляется через `git worktree remove`; незакоммиченные изменения и доказательства сначала сохраняются.

## Шаг 3. Заполните контракт задачи {#task-contract}

Скопируйте шаблон в описание изменения. Пустое обязательное поле означает, что исполнение ещё не подготовлено. У каждого затронутого репозитория кода свои строки: один общий SHA их не заполняет.

```markdown
# EXP-001: <наблюдаемый результат>

Продукт: a
Исходный запрос: <ссылка на задачу трекера>
Владелец результата и ревьюер: <роли и согласованные участники>
Store требований: <адрес product-specs, полный SHA коммита с утверждёнными требованиями>
Контекст метарепозитория: <коммит>
Репозиторий кода web и исходный SHA: <адрес, полный SHA>
Репозиторий кода api и исходный SHA: <адрес, полный SHA>
Рабочая ветка и каталог: <для каждого затронутого репозитория: ветка, абсолютный путь>
Разрешено: <операции, каталоги, команды>
Приёмка: <проверяемые примеры и источник ожиданий по каждому репозиторию>
Пределы и остановка: <время, расходы, повторы, эскалация>
Результат: <по каждому репозиторию: MR, проверенный SHA, ссылки на проверки>
Выпуск: <по каждому сервису: версия и доказательство либо «ещё не выполнен»>
```

## Шаг 4. Оформите изменение в OpenSpec {#change-example}

Условная задача `EXP-001`: пользователь должен выгружать только отфильтрованные строки в CSV. Веб-интерфейс <code class="meta-token">web</code> запускает выгрузку, сервис <code class="meta-token">api</code> фильтрует строки и формирует файл. Изменение одно, а кода — в двух репозиториях, поэтому проверки и слияния у них будут отдельными.

**Согласовать намерение.** В Jira остаются запрос и статус. В `intents/exp-001-export.md` метарепозитория записываем проблему, границы и ссылку на задачу. Пока файл не принят в main, ссылка из Jira-задачи ведёт на него в ветке изменения. Замысел — дополнительный артефакт нашей договорённости, не обязательный файл стандартной схемы OpenSpec.

**Подготовить изменение.** Если изменение ещё не создано в разделе [«Store: конфигурация и подключение»](#store), создайте его из рабочей копии репозитория кода: строка `store:` направит команду в Store.

Дальше агент по [схеме spec-driven OpenSpec](https://openspec.dev/docs/schemas/spec-driven) готовит `proposal.md`, delta-спецификацию в `specs/` и `tasks.md`. `design.md` пишет архитектор — по признакам схемы или при споре; в EXP-001 затронуты два сервиса, поэтому `design.md` нужен. Приёмка описывает фильтрацию, пустой результат и формат CSV. Собственных `specs` и `changes` в репозиториях кода нет: изменение и его архив живут в Store.

**Отправить изменение в Store.** Закоммитьте изменение в отдельной ветке Store и отправьте её: пока этого нет, оно лежит только в вашем клоне. В шаге 5 откройте из этой ветки MR с требованиями (команды отправки ветки — в разделе [«Store: конфигурация и подключение»](#store)).

## Шаг 5. Свяжите запросы изменения и подтвердите результат {#merge-requests}

**Связать запросы изменения: требования — до кода, архив — после.** Запрос требований идёт в Store <code class="meta-token">product-specs</code> и содержит предложенное изменение и спецификации. Запросы кода идут отдельно в каждый затронутый репозиторий, <code class="meta-token">web</code> и <code class="meta-token">api</code>: в них код, тесты и задачи реализации, ссылка на одобренный коммит требований и собственный полный SHA. Запрос архива идёт в Store и выполняется только после слияния всех запросов кода.

Требования одобряет владелец продукта; код принимает техлид по каждому репозиторию. Одобрение и принятие — разные действия. Изменение требований во время работы требует повторного ревью затронутого контекста.

**Завершить в согласованном порядке.** Для этого примера сначала сливаем проверенные запросы кода в обоих репозиториях; затем в запросе архива обновляем действующие спецификации в Store, архив изменения и ссылки на итоговый SHA каждого репозитория. После проверки соответствия сливаем запрос архива. Между слияниями задача остаётся незавершённой.

Такой порядок фиксируем до начала работы: Store и репозитории кода не дают атомарного слияния, а действующая спецификация не должна объявлять ещё нереализованное поведение. Общий Store и идентификатор изменения не означают единый коммит всех сервисов.

**Подтвердить выпуск отдельно.** Слияние кода не доказывает работу в целевой среде. В `evidence/EXP-001.md` сохраняем версию выпуска, проверенный коммит каждого сервиса, ссылки на CI и результат приёмки после выпуска. Если релиз отложен, прямо фиксируем это и оставляем соответствующий статус в трекере. Итоговый отчёт связывает запрос, спецификацию, код и наблюдаемый результат.

## Проверьте результат {#handoff}

Другой участник должен найти исходный запрос, восстановить выбранный контекст и понять, что уже проверено. Перед передачей проверьте: ссылки доступны; SHA указаны; обе части изменения согласованы; результат проверки отличается от результата выпуска; открытые вопросы имеют владельцев. В метарепозитории остаются компактные выводы и ссылки, а подробные логи — в предназначенном для них хранилище.

<ul class="check">
<li>По задаче находятся продукт, владелец, Store с каноническими требованиями и репозитории кода.</li>
<li>В контракте заполнены коммит Store, исходные SHA каждого репозитория, рабочая ветка, каталог, разрешённые действия и приёмка.</li>
<li><code>rev-parse HEAD</code> в каждой рабочей копии показывает согласованный SHA своего репозитория.</li>
<li><code>openspec store doctor product-specs</code> показывает <code>Issues: none</code>, а изменение лежит в <code>product-specs/openspec/changes/</code> и отправлено в GitLab.</li>
<li>Предложение OpenSpec описывает поведение и проверяемые сценарии; форма и смысл проверены отдельно.</li>
<li>Запросы изменения связаны; код каждого сервиса указывает коммит одобренного предложения.</li>
<li>После реализации обновлены действующие спецификации и архив в Store, указан итоговый SHA каждого репозитория.</li>
<li>Результат выпуска подтверждён отдельно либо явно отмечен как ещё не выполненный.</li>
<li>При внешнем источнике требований сохранён указатель, а не вторая каноническая копия.</li>
</ul>
